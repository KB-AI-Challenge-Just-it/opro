# 기술 명세서 참고 자료 — 예선 평가 기준별 정리

> **문서 목적**: 예선 평가 기준(문제해결능력 50점 + 기술적 완성도 50점) 각 세부 항목에 맞춰, 지금까지 실제로 구현·검증된 내용을 코드 근거와 함께 정리한다. 대회 제출용 기술명세서 작성 시 이 문서의 문단을 그대로 가져다 쓰거나 요약해서 쓸 수 있도록, 이미 완성된 프로즈(prose) 형태로 작성했다.
> **근거 기준**: 여기 담긴 내용은 전부 실제 코드(`apps/api-core`, `apps/ai-engine`, `apps/web`)·DB 스키마(`db/init/*.sql`)·git 이력·기존 조사 문서(`doc/planning/prd.md`, `doc/2026-07-28/*`)를 대조해 검증한 사실만 담았다. 계획 단계 아이디어와 실제 구현이 다른 경우, **실제 구현을 기준으로 서술**했다.

## 1. 문제해결능력 (50점)

### 1-1. 문제 정의 및 필요성 (15점)

**문제의 본질**: 소상공인은 경영에 직접 영향을 주는 정보(상권 변화, 금리 변동, 신규 정책자금 공고 등)를 놓치기 쉽다. 정보가 존재하지 않는 것이 아니라, **여러 채널에 흩어져 있고 변화가 생겼을 때 사용자에게 먼저 알려주는 주체가 없다**는 것이 핵심 문제다. 기존 서비스는 대부분 사용자가 스스로 검색·조회해야 답을 주는 **반응형(reactive) 구조**이며, 이 프로젝트는 에이전트가 상황을 상시 모니터링하다 먼저 개입하는 **능동형(proactive) 구조**를 지향한다.

**기존 서비스 대비 공백 (실제 조사 근거)**: KB국민은행은 이미 소상공인 대상 서비스를 여러 채널로 운영 중이지만, 각 서비스는 아래와 같은 구조적 한계를 가진다.

| 기존 서비스 | 형태 | 한계 |
| --- | --- | --- |
| 상권분석시스템(KB부동산 Liiv ON) | 온라인 리포트 | 조회 시점의 정적 스냅샷만 제공 — 이후 변화가 생겨도 재알림 없음 |
| 우리가게 매출순위·신용도(KB스타기업뱅킹) | 셀프 진단 | 사용자가 직접 앱을 열어 확인해야 함 — 이상 신호를 능동적으로 알리는 기능 부재 |
| KB 소호 컨설팅센터 | 오프라인 상담 | 전국 13개 센터의 예약 기반 상담 — 상시 모니터링·실시간 대응이 구조적으로 불가능 |
| KB상권활성화지수 | B2B/B2G 분석 모델 | 지자체·기관 대상 분석 도구 — 개별 소상공인이 직접 받아보는 서비스가 아님 |
| (경쟁사) 하나은행 | AI 기반 정책자금 맞춤 조회 | 이미 운영 중으로 확인됨 — KB는 개별 소상공인 대상 자동 매칭 서비스가 뚜렷하지 않음 |

또한 상권(Liiv ON) · 매출(스타기업뱅킹) · 정책자금(컨설팅센터) 정보가 각각 다른 채널에 분절돼 있어, 사용자가 여러 곳을 오가며 스스로 정보를 종합해야 한다는 점도 확인했다.

**핵심 포지셔닝**: 이 프로젝트는 KB가 이미 보유한 개별 기능(상권분석·매출진단·컨설팅·정책자금 안내)을 대체하는 새 데이터를 만드는 것이 아니라, **흩어진 기존 기능들을 "상시 감시 + 자동 트리거 + 통합 판단"이라는 에이전틱 구조로 엮어내는 것**이 차별점이다. 이는 대출 상담 연계 등 KB의 기존 비즈니스 모델과도 자연스럽게 이어질 수 있는 확장 지점이다.

### 1-2. 아이디어의 활용 가능성 (15점)

- **KB 기존 채널과의 연계 가능성**: 이 서비스가 만드는 최종 산출물(진단 리포트 + 매칭된 정책자금 + 신청서 초안)은 그 자체로 완결된 상담 결과물이라, KB 소호 컨설팅센터 상담 전 사전 진단 자료로 연계하거나 대출 상담으로 자연스럽게 이어질 수 있는 구조다.
- **파라미터화된 확장 구조**: 업종·지역·임계값을 코드에 하드코딩하지 않는다는 원칙(`CLAUDE.md`)을 프로젝트 전반에 강제했다 — 온보딩의 업종·지역은 자유 입력, 알림 시간(`preferred_notify_hour`)은 계정별 설정값, 매칭 상한(top-5)은 상수 하나로 관리된다. 특정 업종·지역 시나리오에 종속되지 않아, 다른 업종군·다른 지자체로 그대로 확장 가능하다.
- **다중 사용자 구조가 이미 실동작**: 회원가입/로그인, 사용자별 온보딩 프로필·리포트 이력 조회까지 이미 구현돼 있어 "데모 1인 시나리오"가 아니라 실사용자 다수를 전제로 한 서비스 구조를 갖췄다.
- **공공데이터 기반이라 확장 비용이 예측 가능**: 기업마당(정책자금)·한국은행 ECOS(경기지표) 모두 무료 공개 API다. 유료 데이터소스에 의존하지 않아, 다른 지자체·업종으로 확장할 때 비용 구조가 선형적으로 예측 가능하다.
- **패턴 자체의 재사용 가능성**: "온보딩 프로필 → 능동 매칭 → 근거 기반 추천 → 대화형 정제 → 실행 가능한 산출물(신청서 초안)"이라는 파이프라인 구조는 정책자금 도메인에 한정되지 않는다. 세무·법률·노무 등 소상공인이 놓치기 쉬운 다른 행정·금융 정보 도메인에도 같은 아키텍처를 재적용할 수 있다.

### 1-3. 아이디어의 창의성 및 효과 (20점)

- **반응형이 아닌 능동형 에이전트**: 사용자가 검색하지 않아도 배치가 매시간 신규 정책자금을 감지해 먼저 알린다(`ProfileMatchTrigger` + `profile_funding_alert` 중복 차단). 위 1-1에서 확인했듯 기존 KB 서비스·경쟁사 서비스 대부분이 반응형인 시장에서, "먼저 찾아서 알려주는" 구조 자체가 차별점이다.
- **단발성 매칭이 아닌 대화형 2단계 컨설팅**: 온보딩 직후 곧바로 리포트를 주지 않고, ① Claude Opus가 프로필만으로 개인화 진단문과 2~4개의 검증 재질문을 먼저 생성하고 ② 사장님이 재질문에 답하면 그 답변을 반영해 Sonnet이 매칭·리포트를 생성하는 2콜 구조를 도입했다. "내가 방금 답한 것이 결과에 실제로 반영된다"는 체감을 만드는 설계로, 자동 생성 리포트가 사장님의 실제 상황을 충분히 반영하지 못한다는 문제의식에서 나온 개선이다.
- **"모델을 못 믿는다"는 전제를 코드로 강제**: LLM이 출력 형식·판정 계약을 어길 수 있다는 것을 실측으로 확인한 뒤(부적격 공고에 관련도 점수가 함께 출력되는 사례), 프롬프트 지시에만 의존하지 않고 ai-engine과 Spring 백엔드 두 지점에서 각각 독립적으로 결과를 재검증하는 이중 방어 구조를 만들었다. AI 기능을 "믿고 쓰는" 것이 아니라 "검증하며 쓰는" 신뢰성 있는 시스템 설계로 이어진 창의적 해법이다.
- **자체 QA로 발견한 UX 문제를 능동적으로 재설계**: 실사용 데이터를 검토하던 중, 배치가 재매칭할 때마다 리포트에 "새로 찾은 공고만" 나열되는 방식이 실제로는 새로 게시되지 않은 오래된 공고를 "새 매칭"으로 오인시키고, 리포트마다 추천 목록이 통째로 바뀌어 사용자가 이전 추천과 무관한 결과로 오해할 수 있다는 문제를 스스로 발견했다. 이를 "프로필 기준 누적·재정렬 목록"(신규 매칭은 점수가 충분히 높을 때만 상위 5개 안에 진입, 마감 지난 공고는 자동 제외)으로 재설계하고, "새 공고" 표시 기준도 재검토를 거쳐 실제 경과 시간(3일) 기준으로 다시 다듬었다. 외부 사용자 피드백이 아니라 **실사용 데이터를 스스로 검증해 제품 결함을 찾고 고치는 과정** 자체가 이 프로젝트의 개발 방식을 보여주는 사례다.
- **정보 제공에서 행동 지원까지 확장**: 대부분의 정책자금 매칭 서비스는 "이런 지원사업이 있다"는 정보 전달에서 그친다. 이 서비스는 매칭된 공고마다 신청서 초안(사업개요·신청사유·활용계획·기대효과 4섹션)을 AI가 작성해, 정보 제공을 실제 신청 행동으로 이어지게 한다. 단, 정부 포털 실제 제출은 사용자 본인 책임 영역으로 명확히 남겨(자동 제출 기능 미구현), 신뢰성과 책임 소재를 분리했다.
- **실패에 관대한 알림 설계**: 인앱 알림(원본, 필수 경로)과 카카오 "나에게 보내기"(미러, 선택 경로)를 계층화해, 카카오 API 장애가 핵심 알림 기능을 막지 못하도록 설계했다. "소상공인은 카톡에 산다"는 사용자 채널 통찰과, 외부 API 의존성에 대한 장애 격리 설계를 함께 반영한 지점이다.

## 2. 기술적 완성도 (50점)

### 2-1. 기술 적정성 (20점)

**서비스 경계와 책임 분리**: Next.js(웹) · Spring Boot(백엔드, 유일한 데이터 오너) · FastAPI(AI 서비스, 무상태)의 3계층 구조를 코드 레벨에서 강제한다. `api-core`(Spring)에는 `anthropic` SDK 의존성이 전혀 없으며, 모든 LLM 호출은 `AiEngineClient`라는 단일 HTTP 클라이언트를 거친다. `ai-engine`은 `business_profile`·`report`·`app_user` 등 비즈니스 테이블을 직접 조회하지 않고 Spring이 컨텍스트를 담아 호출한다. 이 원칙 덕분에 AI 서비스 계층을 독립적으로 교체·확장할 수 있고, 인증·트랜잭션 등 상태 관리는 전부 한 곳(Spring)에 모여 일관성을 유지한다.

**목적에 맞는 모델 티어링**: 모델 배분 기준을 비용이 아니라 **그 단계가 틀렸을 때 이후 단계에 미치는 영향**으로 잡았다.

| 모델 | 호출처 | 이유 |
| --- | --- | --- |
| Claude Opus 4.8 | 콜1 개인화 진단 (1곳) | 이후 재질문·매칭·리포트 전체의 입력이 되는 유일한 단계라 최상위 품질 배치 |
| Claude Sonnet 4.6 | 적합성 판단(L3)·리포트 합성(L5)·신청서 초안 (3곳) | 판단·서술이 필요한 추론 작업 |
| Claude Haiku 4.5 | 검색 쿼리 변환(L4) (1곳) | 판단이 아닌 기계적 재작성 작업 |

**검색은 언어모델이 하지 않는다**: 키워드 검색(BM25, `rank-bm25` + `kiwipiepy` 한국어 형태소 분석)과 벡터 검색(ChromaDB + `BAAI/bge-m3`, 1024차원 다국어 임베딩)을 RRF(Reciprocal Rank Fusion, k=60)로 앙상블한 뒤, 언어모델은 이 결과를 판단·서술하는 데만 쓴다. 지역·업종 일치나 마감일처럼 참/거짓이 명확한 판정, 매출 규모처럼 정확해야 하는 수치는 코드가 계산해 근거로 전달한다. 벡터스토어를 Chroma로 단일화한 것도 실용적 트레이드오프 판단이었다 — pgvector로 교체하면 AI 서비스 전면 재작성이 필요한 반면, Chroma는 임베딩 함수를 직접 지정할 수 있어 한국어 모델(bge-m3) 제어가 용이했다(기본값은 영어 특화 모델이라 그대로 두면 한국어 의미 검색 품질이 열화됨).

**모델이 계약을 어길 수 있다는 전제 위의 방어적 설계**: 부적격(INELIGIBLE)으로 판정된 공고의 관련도 점수는 ai-engine 응답 파싱 직후와 Spring 저장 직전 두 지점에서 각각 독립적으로 강제 삭제한다. 이 이중 검증은 회귀 테스트로 고정돼 있어, 모델이 계약을 위반하는 응답을 반환해도 최종 결과에서는 반드시 제거된다.

**운영 인프라**: 프롬프트 캐싱(반복 컨텍스트에 `cache_control: ephemeral` 적용), 모든 호출의 토큰 사용량 로깅(input/output/cache read/cache write), 응답이 `max_tokens`로 강제 종료됐는지 감지하는 잘림 경고, `MOCK_LLM` 환경변수로 전 서비스 배선을 토큰 비용 없이 검증할 수 있는 목업 전환 스위치까지, 실제 운영을 전제로 한 공통 인프라를 갖췄다.

### 2-2. 개발 계획의 구체성 (15점)

**단계적 MVP 범위 관리**: 초기 기획(PRD v1.2) 단계에서부터 "1개 업종 × 1개 지역 시나리오에서 감지→분석→매칭→제안이 실제 데이터로 end-to-end 동작"을 성공 기준으로 명시하고, 넓게 벌리다 일부가 목업으로 채워지는 것보다 좁고 확실하게 도는 것을 개발 우선순위로 잡았다. 4개 데이터소스(상권·경기지표·소비트렌드·정책자금) 중 확보 난이도가 가장 높은 소비 트렌드 축은 처음부터 대체 지표로 처리하기로 계획해, 실현 가능성이 낮은 부분을 미리 걷어내고 시작했다.

**이슈·브랜치 단위 추적 개발**: 기능 단위를 GitHub 이슈로 먼저 정의하고, 이슈별 브랜치에서 구현 후 PR로 병합하는 프로세스를 전 개발 기간 일관되게 유지했다. 예를 들어 "임계값 트리거를 프로필 기반 매칭으로 전환"은 이슈 #29로, "부적격 공고 사전 배제"는 이슈 #124로, "누적 매칭 리스트 전환"은 이슈 #139로 각각 추적되며, 코드 커밋·PR 설명에 항상 이슈 번호가 남아 결정의 배경을 되짚을 수 있다.

**계획과 실측을 근거로 한 아키텍처 재조정**: 개발 계획이 고정된 문서가 아니라 실측 데이터를 근거로 갱신되는 과정을 거쳤다. 대표적으로 "상권·경기지표 같은 전국 단일 계열 지표는 개인화된 트리거로 쓰기 어렵다"는 판단(이슈 #29)에 따라 임계값 기반 트리거 구조를 전면 폐지하고 온보딩 프로필 기반 능동 매칭으로 전환했으며, 이후 "자동 생성 리포트가 사장님의 실제 상황을 충분히 반영하지 못한다"는 문제의식으로 대화형 2콜 컨설팅을 도입하는 등, 최소 세 차례의 방향 전환이 각각 문서화된 이유와 함께 이뤄졌다.

**AI 하네스 기반 병렬 개발 프로세스**: 개발 자체를 역할별 전문 에이전트(backend-dev·ai-dev·web-dev·qa-verifier)와 오케스트레이션 스킬로 구조화해, 의존성이 없는 작업(예: 백엔드의 수집기 수정과 AI 서비스의 인덱싱 필터 수정)을 파일시스템 경계 기준으로 분리해 병렬로 진행했다. 이 병렬 실행은 GitHub 이슈·PR 생성/종료 타임스탬프가 초 단위로 겹치는 것으로 실증됐다(예: 이슈 3건이 22초 이내에 연달아 생성되고 16초 이내에 함께 종료된 사례). 계약(인터페이스)을 먼저 확정한 뒤 양쪽을 병렬로 구현하는 "계약 우선 설계" 패턴을 반복 적용했다.

### 2-3. 기술 실현 가능성 (15점)

**이미 end-to-end로 동작하는 시스템**: 온보딩 제출 → 개인화 진단(Opus) → 재질문 응답 → 매칭(하이브리드 RAG) → 적합성 판단·자격 게이팅(Sonnet) → 리포트 생성(Sonnet) → 단일 트랜잭션 저장 → 인앱/카카오 알림까지, 전체 파이프라인이 개념 검증(PoC) 단계가 아니라 실제로 동작하는 코드로 구현돼 있다. 배치 경로(매일 06:00 수집·인덱싱, 매시간 프로필 재매칭)도 `@Scheduled` 작업으로 실제 가동 중이다.

**실 데이터 기반 검증**: 기업마당(정책자금 공고)·한국은행 ECOS(경기지표) 공공 API로 실데이터를 수집해 정책자금 공고 1,500여 건을 색인하고, 실제 회원 프로필로 매칭·리포트 생성까지 검증했다. 목업이 아닌 실제 정부 공개 데이터를 파이프라인 전 구간에서 사용한다.

**자체 발견·해결한 실측 이슈들이 실현 가능성을 방증**: 개발 과정에서 실제로 부딪힌 문제와 해결을 코드 근거와 함께 남겼다 —

- 모델이 출력 계약을 지키지 않는 사례(부적격 공고에 점수 출력)를 발견해 API 경계 이중 검증으로 봉쇄
- 응답 형식을 강제하는 프리필 기법이 진단에 쓰는 모델에서 요청 자체가 거부되는 것을 실측(400 오류)하고, 관대한 파싱 체인으로 대체
- 온보딩 매칭 폴링이 실측 처리 시간(약 57초)과 타임아웃(60초)이 거의 맞붙어 처리 중에 완료 화면이 뜨는 문제를 발견해 1차로 대증 치료(타임아웃 확대) 후 아키텍처 자체를 재설계(폴링 대신 직접 응답 대기)해 문제 유형을 근본적으로 제거
- 실사용 리포트 데이터를 비교 검토해 "새 매칭" 판정 로직의 결함(공고 최신성이 아니라 알림 이력만 확인)을 스스로 찾아내 누적·재정렬 목록 + 시간 기반 재판정으로 개선

**기술부채에 대한 자기 점검과 정직한 정리**: 상권 데이터 수집기(소진공 상권정보 API 연동)를 조사하던 중, 이 수집기가 저장하는 코드 체계와 온보딩이 실제로 발급하는 코드 체계가 애초에 달라 실사용자에게는 한 번도 정상 동작한 적이 없는 죽은 기능이라는 것을 스스로 발견했다. 지오코딩·상권코드 매핑 인프라 없이는 근본 해결이 불가능하고 핵심 가치(정책자금 매칭)와 무관하다고 판단해, 범위를 축소하는 대신 기능 자체를 코드에서 완전히 제거했다 — "동작하는 것처럼 보이는 코드"를 남겨두지 않는 기술적 정직성을 실제 커밋 이력으로 증명할 수 있다.

**회귀 방지 체계**: ai-engine 자동화 테스트(90건 통과), api-core 유닛 테스트, 프론트엔드 타입 검사(`tsc --noEmit`)를 각 변경마다 실행해 검증한다. 기능 변경 시 "구현했다"가 아니라 "테스트로 통과를 확인했다"는 근거를 남기는 것을 개발 관행으로 유지했다.
