# "매칭 없음" 조사 기록 + 로컬 개발 DB 리셋 흐름 정리

> **문서 목적**: 로컬 개발 중 DB를 초기화한 뒤 "매칭이 안 되는" 것처럼 보이는 상황을 조사하며 확인한 두 가지 — ① 로컬 DB 리셋 후 데이터가 실제로 어떻게 다시 채워지는지, ② 특정 프로필(충남 지역)에서 실제로 발견한 지역 하드필터 결함 — 을 근거와 함께 기록한다.

---

## 1. 로컬 DB를 초기화하면 정말 데이터가 없어지는가

**결론: 아니오.** `docker compose down` 후 `pg-data`/`chroma-data` 볼륨을 지우고 다시 올려도, 컨테이너가 뜨는 순간 자동으로 실 데이터가 재수집된다.

### 왜 그런가 — `StartupDataSeeder`
- 정기 수집은 `ScheduledJobs.collectAndIndex()`가 **매일 06:00(KST)** 1회 담당한다.
- 하지만 로컬 개발 환경은 새벽 6시에 켜져 있으리라는 보장이 없다. 이 공백을 메우려고 `StartupDataSeeder`(`apps/api-core/.../pipeline/StartupDataSeeder.java`)가 별도로 존재한다.
- 앱이 기동될 때마다(`ApplicationReadyEvent`) `SELECT count(*) FROM policy_announcement WHERE pblanc_id NOT LIKE 'DEMO-%'`로 **실 데이터 건수**를 확인하고, 0건이면 06:00을 기다리지 않고 즉시 수집(`BizinfoCollector`·`EcosCollector`)과 색인 재구성(`/index/rebuild`)을 별도 가상 스레드에서 돌린다.
- 실 데이터가 이미 있으면(재기동일 뿐 리셋이 아니면) 스킵해서 API를 낭비하지 않는다.

### 실제로 확인한 값 (2026-07-30, DB 리셋 직후)
```
[startup-collect] 실 데이터 없음(시드만 존재) — 자동 수집 시작
...
GET /api/agent/collect/status → {"seedOnly":false,"total":1508,"realCount":1508}
POST /index/rebuild → {"indexed":1508}
```
Chroma 컬렉션(`policy_announcements`)도 `BAAI/bge-m3` 임베딩 함수로 정상 생성되어 1,508건이 색인된 것을 API로 직접 확인했다.

**따라서**: "DB를 초기화했고 마침 6시가 아니라서 데이터가 없다"는 추론은 이 프로젝트에는 적용되지 않는다. 리셋 직후 컨테이너를 올리기만 하면 몇 분 내로(수집 API 응답 + bge-m3 콜드로드 임베딩 시간) 실 데이터가 채워진다.

## 2. 매칭은 정확히 어디서 이뤄지는가 (요약)

1. `ai-engine`의 `/matching`(L4, `hybrid_search.py`)이 쿼리 변환(Haiku) → BM25(각 축 top-20) ∥ 벡터(bge-m3, top-20) 검색 → RRF(k=60) 융합 순서로 후보를 추린다.
2. RRF로 정렬된 순서대로, **하드필터(지역·업종) 통과분만** top-5에 채운다. 각 후보의 상세 필드(`title`/`region`/`target`/`summary_html` 등)는 그때그때 PostgreSQL `policy_announcement`에서 직접 SELECT한다 — DB에 데이터가 있어야만 후보가 나올 수 있다.
3. 하드필터를 통과한 결과가 있어야 L3(적합성 설명·Sonnet)·L5(리포트 생성·Sonnet)로 넘어간다. 하드필터 통과분이 0건이면 `/matching`이 빈 배열을 반환하고, `ConsultationService.specialize()`가 `status: "NO_MATCH"`로 응답한다 — 이때 화면에 "지금 조건에 맞는 정책자금을 찾지 못했어요" 화면이 뜬다.

## 3. 실제 사례 조사 — profile_id=2 (숙박업 · 충남 논산시)가 0건인 이유

DB 리셋 이후 실데이터(1,508건)로 새로 온보딩한 프로필 2번(숙박업, 충남 논산시)이 두 번의 컨설팅 세션에서 모두 `NO_MATCH`가 나왔다. "데이터가 없어서"가 아니라 **지역 하드필터(`_region_result`, `hybrid_search.py`)의 실제 결함** 때문임을 확인했다.

### 확인 과정
- `/matching`에 이 프로필 조건을 직접 넣어 호출 → `{"matches": []}` (실측 확인).
- DB에는 관련 후보가 이미 존재한다:
  - `region ILIKE '%충청남도%'` 49건
  - `target/summary ILIKE '%숙박%'` 26건
  - 그런데도 하드필터를 통과한 게 하나도 없었다.

### 근본 원인 — 두 가지가 겹쳤다

**① 시/도 축약형 vs 정식 명칭 불일치.** 온보딩 시/도 선택지는 축약형(`"충남"`, `"경북"`, `"전남"` 등)을 쓰는데(`apps/web/app/onboarding/page.tsx`의 `SIDO_OPTIONS`), 공고의 `region` 컬럼은 기업마당 원문 그대로 정식 명칭(`"충청남도"`, `"경상북도"`)이 들어간다. `_region_result`는 프로필 값이 공고 `region` 문자열의 부분문자열인지만 검사하는데, `"충남"`은 `"충청남도"`의 부분문자열이 아니다(충-**청**-남-도 — 가운데 "청"이 끼어 끊긴다). 그 결과 **충청남도 소재 공고 49건이 이 프로필에서 전부 제외**된다.

똑같은 문제가 발생하는 축약형: **충남/충북/경남/경북/전남/전북** — 이 6개 도는 "OO도"에서 가운데 글자(청/상/라)가 생략된 축약형이라 정식 명칭의 연속 부분문자열이 아니다. (반면 경기/강원/제주/서울/부산 등은 축약형이 정식 명칭의 접두어라 문제없이 통과한다.)

**② 중앙부처 발주 공고의 지역 컬럼이 "전국"이 아니라 부처명.** `_region_result`는 `region`이 비어있거나 `"전국"`이라는 글자를 포함하면 무조건 통과시키는데, 중앙부처가 낸 공고는 `region` 컬럼에 `"전국"`이 아니라 **발주 기관명**이 그대로 들어간다(`BizinfoCollector`가 기업마당 `jrsdInsttNm` 필드를 그대로 옮겨 저장하기 때문). 실측 확인:

| region 값 | 활성 공고 수 |
| --- | --- |
| 중소벤처기업부 | 141 |
| 산업통상부 | 92 |
| 고용노동부 | 56 |
| (충청남도, 참고용) | 49 |

이 부처명들은 "전국"이라는 글자를 포함하지 않고, 어떤 프로필의 시/도·시군구와도 부분문자열로 겹치지 않으므로 **모든 프로필에서 예외 없이 탈락**한다. 활성 공고 1,508건 중 약 289건(≈19%)이 이 경로로 사실상 전 사용자에게 원천 배제되고 있다.

### 결론
"충남 논산시 숙박업 프로필에 진짜로 맞는 공고가 없다"가 아니라, **지역 하드필터가 정상적으로 통과시켰어야 할 후보(도 단위 49건 + 전국 단위 289건)를 문자열 불일치 때문에 걸러낸 것**이 0건의 실제 원인이다. 위 6개 도 프로필 전체 + 중앙부처 발주 공고 전체(전 사용자 공통)에 영향을 주는, 이번 조사에서 처음 발견한 매칭 파이프라인 결함이다.

**이번 작업 범위에서는 수정하지 않았다** — 별도 이슈로 분리해 논의 후 처리할 예정.

## 4. "프로필·조건 다시 확인" 버튼 — 동작 변경

### 배경
매칭 없음 화면의 "프로필·조건 다시 확인" 버튼이 `/onboarding`(새 질문지 제출 화면)으로 이동시켰는데, 실제로는 문제가 있었다:
- `OnboardingController.submit()`은 항상 새 `business_profile` row를 INSERT한다 — 기존 프로필을 수정하는 게 아니라 **완전히 새 프로필을 하나 더 만드는** 동작이었다.
- 이 서비스엔 애초에 기존 프로필을 수정(PUT/PATCH)하는 기능 자체가 없다. 업종·지역·매출 같은 값은 사업 자체의 사실이라 "수정"할 대상이 아니기도 하다.
- `hourlyMatchTrigger()`가 매시간 `biz_status='ACTIVE'`인 프로필을 자동으로 재매칭하고 있어서, 새 공고가 올라오면 사용자가 아무것도 안 해도 알림이 간다 — "다시 확인" 버튼이 매칭을 다시 유발할 필요가 없었다.

### 결정
편집 기능을 새로 만드는 대신, 버튼은 **"내가 제출했던 내용을 읽기 전용으로 다시 보기"**로만 동작하도록 바꿨다(기존에 있던 `/profiles/[id]` 읽기 전용 페이지로 연결). 이후 자동 재매칭은 배치가 알아서 처리한다는 걸 문구로도 명시했다.

### 변경 내역 (`apps/web/app/consult/[sessionId]/page.tsx`)
- 버튼 `onClick`: `router.push("/onboarding")` → `router.push(`/profiles/${profileId}`)` (profileId는 이미 세션스토리지에서 로드돼 있어 항상 존재)
- 버튼 문구: "프로필·조건 다시 확인" → "내가 답한 내용 다시 보기"
- 안내 문구: "프로필이나 사업 조건을 다시 살펴보면 다른 결과를 확인할 수 있어요" → "이후 새로운 정책자금이 올라오면 저희가 먼저 찾아서 알려드릴게요"(자동 재매칭이 있다는 사실과 실제 동작을 일치시킴)
