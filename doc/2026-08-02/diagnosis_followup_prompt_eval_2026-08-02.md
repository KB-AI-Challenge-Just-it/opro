# 진단(콜1) 재질문 프롬프트 — 2단계 실측 베이스라인 (2026-08-02)

## 배경

`apps/ai-engine/app/services/diagnosis.py`의 `SYSTEM` 프롬프트는 온보딩 프로필을 보고 경영 진단과
검증 재질문(`follow_up_questions`, 2~4개)을 함께 생성한다. 이 프롬프트를 성능 튜닝하려면 감이 아니라
근거가 필요한데, 이 문서 이전에는 `test_diagnosis.py`가 JSON 계약(파싱·필드 존재)만 검증했지
"재질문이 실제로 규칙을 지키는가", "얼마나 자주 깨지는가"를 재는 수단이 없었다.

이 문서는 그 첫 실측 — 골든 프로필 8종에 실제 Opus를 호출해 얻은 베이스라인과, 거기서 나온 두 가지
실제 문제를 원인까지 분석한 기록이다.

## 먼저 용어 정리 — HARD와 SOFT가 뭔가

AI가 만든 재질문("사장님, 최근 매출이 어떤가요?" 같은 것) 하나하나를 사람이 매번 눈으로 읽고 "이거
괜찮나?" 판단하면 시간이 너무 오래 걸린다. 그래서 "이건 무조건 지켜야 하는 규칙"과 "이건 애매해서
사람이 한 번 더 봐야 하는 것"을 나눠서, 컴퓨터가 자동으로 1차 채점을 하게 만들었다. 그 두 등급이
HARD와 SOFT다.

- **HARD = "이건 명백히 틀렸다."** 예를 들어 "재질문은 2~4개만 만들어라"는 규칙을 AI에게 미리
  지시해뒀는데, 실제로 5개나 1개가 나오면 그건 볼 것도 없이 규칙 위반이다. 객관식 질문인데 선택지가
  2개뿐이라거나, 주관식인데 선택지가 딸려 나오는 것도 마찬가지 — **정답이 명확해서 컴퓨터가 100%
  확신을 갖고 "틀렸다"고 말할 수 있는 것**만 HARD로 분류한다.
- **SOFT = "이건 문제일 수도 있는데, 확실친 않다."** 대표적인 예가 "온보딩에서 이미 답한 걸 또
  묻는가"다. 이건 사람이 읽으면 바로 판단되지만, 컴퓨터는 문장의 의미를 완전히 이해하지 못하니까
  **비슷한 단어가 겹치면 일단 "의심"** 표시만 해둔다. 예를 들어 사장님이 온보딩에서 "체납 있음"이라고
  이미 답했는데, 재질문에 "체납"이라는 단어가 또 나오면 SOFT로 걸린다. 그런데 실제로는 "체납이
  있나요?"를 또 묻는 게 아니라 "그 체납을 정리 중이신가요?"처럼 **한 단계 더 자세히 캐묻는 좋은
  질문**일 수도 있다 — 그래서 SOFT는 "위반 확정"이 아니라 "사람이 한 번 확인해봐" 딱지에 가깝다.

비유하자면 HARD는 시험 채점기가 "빈칸을 안 채웠다" 같은 명백한 실수를 잡아내는 것이고, SOFT는
"이 답이 표절인 것 같다"처럼 표절 검사기가 유사도만 보고 일단 표시해두는 것과 비슷하다 — 표시가 됐다고
무조건 진짜 표절인 건 아니고, 사람이 마지막으로 확인해야 한다.

이 구분이 왜 중요하냐면, 아래 결과표에서 "SOFT 위반 4건"을 보고 "재질문 절반이 잘못됐다"고 오해하면
안 되기 때문이다. 실제로 이번 8건을 사람이 다 읽어봤더니 SOFT로 걸린 것 중 대부분은 "의심만 됐지 실제
문제는 아니었다"(아래 "문제 2" 참고). SOFT는 사람의 최종 확인이 필요한 후보 목록이지, 확정된 결함
목록이 아니다.

## 어떻게 호출했는지

### 1단계 — 하드 룰 채점기 (토큰 소모 없음, 먼저 구축)

- `apps/ai-engine/app/services/diagnosis_rules.py` — `diagnosis.SYSTEM`이 스스로 선언한 재질문 규칙을
  코드로 채점하는 순수 함수 `check_follow_up_rules(profile, result)`. HARD/SOFT 정의는 위 "용어 정리"
  참고 — HARD는 재질문 개수(2~4개)·`id` 누락/중복·`type` 값·choice 옵션 개수(3~5개) 같은 형식 규칙,
  SOFT는 이미 채워진 프로필 필드를 키워드 매칭(`_FIELD_KEYWORDS`)으로 다시 묻는 것으로 "의심"되는 경우.
- `apps/ai-engine/app/services/golden_profiles.py` — 업종·정보완결도(전부 채움/대부분 모름)·재무상태
  (체납·연체 있음/없음/모름)를 다르게 조합한 골든 프로필 8종. `cafe_full`(정보 완결) ~
  `retail_unknown_finance`(재무 정보 대부분 미상)까지 폭을 덮는다.
- `apps/ai-engine/tests/test_diagnosis_rules.py` — 위 채점기 자체가 맞게 동작하는지 canned
  정상/위반 응답으로 검증하는 회귀 테스트 11개. **실제 LLM 호출 없음** — mock 데이터로 채점 로직만 고정.

### 2단계 — 실제 Opus 호출 (이번에 처음 실행, 토큰 소모)

- `apps/ai-engine/scripts/eval_diagnosis_golden.py` — 골든 프로필 8종 각각에 대해
  `diagnosis.diagnose(profile, econ_context=SAMPLE_ECON_CONTEXT)`를 **실제 Anthropic API**로 호출
  (`model_diagnosis = claude-opus-4-8`, `.env`의 `ANTHROPIC_API_KEY` 사용, `mock_llm=false`).
  - `econ_context`는 `{"기준금리": 3.5, "BSI": 78}` 고정값 — 실제 서비스에서는 Spring
    (`ConsultationService.fetchEconContext`)이 `econ_indicator` 테이블 최신값을 넘기지만, 이 스크립트는
    그 변수 자체가 결과에 섞이는 걸 막으려 대표값 하나로 고정했다.
  - `profile_facts`(결정론적 팩트시트, `ProfileFacts.compose()`)는 Java 쪽에서만 조립되므로 이 Python
    단독 스크립트에서는 **전달하지 않았다** — 이번 베이스라인은 실제 콜1 호출보다 컨텍스트가 하나 적은
    상태다(아래 "한계" 참고).
  - 각 호출 결과(`diagnose()`가 반환한 최종 dict)를 1단계 채점기에 그대로 통과시켜 hard/soft 위반을 집계.
  - 원본 요청/응답/위반 내역을 프로필별 JSON으로 저장(`scripts/output/20260802T072849Z/*.json`), 같은
    프롬프트 버전을 두 번 호출하지 않고 재분석할 수 있게 함.
- 실행 명령: 저장소 루트 `.env`를 `source`해 `ANTHROPIC_API_KEY`를 셸에 로드한 뒤
  `apps/ai-engine`에서 `python scripts/eval_diagnosis_golden.py`.

## 왜 문제인지 — 원인 분석

### 문제 1. 구조적으로 깨진 JSON이 관대한 파싱도 못 살린다 (파싱 실패 12.5%)

`education_no_region_detail` 원본(`scripts/output/20260802T072849Z/education_no_region_detail.json`)을
열어보면, 모델은 재질문 4개를 포함해 완전한 JSON을 만들었다. 그런데 `diagnosis` 문자열이 끝나는
지점에 불필요한 `]` 문자가 하나 더 섞여 있다:

```
...유리한 방향이라고 볼 수 있습니다."], "follow_up_questions": [...
```

닫는 따옴표(`"`) 바로 뒤에 `]`가 하나 더 붙어 있어 이 시점부터 JSON 문법이 깨진다. `diagnosis.py`의
관대한 추출(`re.sub`로 무효 이스케이프만 정리, 첫 `{`~마지막 `}`만 자르기)은 **문법적으로 어긋난 괄호를
복구하는 로직이 아니라서** 이 케이스를 못 잡고, 결국 `json.loads`가 실패해 파일 상단의 docstring이
이미 경고했던 그 폴백 경로(`{"diagnosis": raw, "follow_up_questions": []}`)로 떨어진다.

**결과적으로 잘 만들어진 재질문 4개가 통째로 유실됐다** — 사용자에게는 재질문 세션 자체가 안 뜬다.
이 사고는 docstring이 "가끔"이라고만 적어뒀던 걸 이번에 처음으로 **8건 중 1건(12.5%)** 이라는 수치로
잡은 것이다. 8건은 통계적으로 이 비율을 확정할 만큼 크지 않지만(2단계 설명 시 언급한 표본 크기 문제),
적어도 "0%가 아니다"는 실측으로 확인됐다.

**왜 프롬프트 문구만으로는 안 고쳐질 가능성이 높은가**: SYSTEM 프롬프트 끝에 이미 "반드시 JSON만
출력", "첫 글자는 반드시 `{`" 같은 형식 경고가 두 번 반복되고 있는데도(53~55행) 이번 실패가 났다.
형식 자체(JSON 시작 여부)는 지켰지만 **문자열 내부의 괄호 균형**이 깨진 것이라, SYSTEM 프롬프트를
더 강하게 경고하는 방향보다는 **파싱 쪽의 관대한 추출 로직을 구조적 오류까지 복구하도록 보강**하는
게 더 직접적인 개선 지점일 가능성이 높다.

### 문제 2. SOFT 휴리스틱 자체의 정밀도 문제 — 오탐 다수, 진짜 결함 1건 은폐

8건 중 4건에서 SOFT 플래그가 떴지만, 각 재질문 문장을 직접 읽어보면 대부분 **키워드만 겹치고
실제로는 새로운 정보를 묻는 질문**이었다:

| 프로필 | 플래그된 질문 | 실제 판단 |
| --- | --- | --- |
| manufacturing_delinquent | "체납·연체 정리를 위해 세무서·은행과 상담 진행 중인가" | 오탐 — 체납 유무가 아니라 해결 진행 상태를 물음(새 정보) |
| lodging_high_revenue | "과거 연체가 해결된 시점은 언제쯤인가" | 오탐 — `overdue_status="있었지만 해결"`을 다시 묻는 게 아니라 시점을 물음 |
| lodging_high_revenue | "성수기·비수기 매출 차이가 큰 편인가" | 오탐 — 매출 액수(`monthly_revenue_band`)가 아니라 변동 패턴을 물음 |
| startup_early | "창업 전 관련 업종에서 경험이 있는가" | 오탐 — 업종명이 아니라 경력을 물음 |
| **etc_industry_recovering** | **"구체적으로 어떤 업종(무엇을 파는 가게)인지 한 줄로 알려주세요"** | **진짜 결함** — 아래 참고 |

마지막 한 건이 진짜 문제다. `etc_industry_recovering` 프로필의 `industry`는 `"기타"`다. 이 값은
문자열로서는 채워져 있어(`_is_filled()`가 `True` 반환) SOFT 판정에서 "이미 채워진 필드"로 취급됐지만,
**"기타"라는 값 자체가 실질 정보를 담고 있지 않다.** 모델이 이걸 알아채고 정확히 "이 값을 알았다면
진단이 더 정확했을 지점"을 짚어 재질문한 것인데, 채점기가 그 좋은 재질문을 **위반으로 잘못 표시**했다.

이건 프롬프트의 문제가 아니라 `diagnosis_rules.py`의 `_is_filled()` 구현이 "기타"·"기타(직접입력 없음)"
같은 카테고리성 무정보 값을 채워진 값과 구분하지 못하는 코드 결함이다.

## 한계

- **profile_facts 미포함**: 실제 서비스는 콜1에 `ProfileFacts.compose()`가 만든 결정론적 팩트시트를
  같이 넘기는데(Java 전용 클래스), 이 Python 단독 스크립트는 이를 재현하지 않았다. profile_facts가
  매출 라벨(연/월) 신뢰 지시에 영향을 주므로, 매출 관련 재질문 품질은 실제 콜1보다 다소 다를 수 있다.
- **표본 크기**: 8건은 "0%가 아니다"를 확인하는 데는 충분하지만, 파싱 실패율(12.5%)이나 SOFT 오탐률을
  통계적으로 신뢰할 만큼의 크기는 아니다. 프롬프트를 실제로 교체하는 최종 판단 전에는 표본을 늘려야 한다.
- **1회성 스냅샷**: Opus 호출은 확률적이라 같은 프로필도 재호출하면 다른 결과가 나올 수 있다. 이 문서의
  수치는 `run_id=20260802T072849Z` 1회 실행 기준이다.
