# 보고서 개인화·전문화 튜닝 계획

**목적**: 최종 보고서(L5 리포트)가 "일반적인 자동 생성물"이 아니라 **사장님을 직접 상담한 전문 에이전트가 쓴 글**처럼 읽히게 만든다.

**전제(프리미엄 전략)**: 토큰·비용이 더 들더라도 개인화·전문성 품질을 우선한다. 단, 서비스 경계 원칙(api-core=데이터 오너, ai-engine=stateless)과 이슈 #76(공고별 실무정보는 카드가 전담)·이슈 #61(공고 원문 재전송 금지)은 지킨다.

**참고 화면(현재 결과 = "before" 기준물)**: `doc/screenshots/온보딩.png`, `doc/screenshots/보고서.png`, `doc/screenshots/정책자금.png`

## 1. 현재 상태 진단 (증거 기반)

세 화면과 코드·DB를 대조해 **세 가지 근본 원인**을 확정했다. 전부 추정이 아니라 코드/DB로 확인함.

### 1-1. 매출 정밀성 오류 — "연매출"을 "월 매출"로 (신뢰도 파괴)

- 온보딩(`doc/screenshots/온보딩.png`): **연매출 1억~3억**
- 보고서(`doc/screenshots/보고서.png`): **"월 1억~3억의 안정적인 매출"** → 12배 틀림
- **근원 = L3(`cause_analysis.py`)**. DB 확인:
  - `business_profile`: `monthly_revenue_band = '1억~3억'`, `revenue_basis = 'ANNUAL'`
  - `analysis_result.cause_text`(report 17)에 이미 `"월 1억~3억 규모의 안정적인 매출"`로 박혀 있음 → L5가 아니라 **L3가 먼저 틀렸고 L5가 그대로 옮김**
- **원인**: 컬럼 이름이 `monthly_revenue_band`라, 모델이 `revenue_basis=ANNUAL`을 무시하고 컬럼명만 보고 "월"이라고 씀. 필드 이름 자체가 함정.

### 1-2. 진단·상권·경기·재질문 답변이 보고서에 전혀 반영 안 됨 (전문성 상실의 핵심)

콜1 진단(대기 화면에서 사장님이 이미 읽은 글)은 상권(반경 500m 경쟁 카페 5곳, 유동인구 0%)·경기(BSI 95)까지 엮어 날카로웠다. 그런데 최종 보고서에는 그 내용이 **하나도 없다.**

- 코드 확인(`PipelineService.run(profileId, newMatches)`): 진입 인자가 `profileId`와 `newMatches`뿐. 프로필을 DB에서 새로 로드하고, **진단 텍스트도 재질문 답변도 받지 않는다.**
- `ConsultationService.specialize`는 진단·답변을 **매칭 쿼리(`buildEnrichedQuery`)에만** 쓴다. 즉 진단·답변은 "어떤 공고가 매칭되는지"에만 영향을 주고, **설명·보고서 문장에는 전혀 흐르지 않는다.**
- 결과: 사장님이 재질문에 공들여 답해도 **"내 답이 결과를 바꿨다"는 체감이 보고서에 0.** 이건 2-콜 설계의 존재 이유 자체가 결과물에서 사라진 것.

### 1-3. L5가 프로필의 핵심 수치를 직접 못 봄 → 부정확한 의역

- `PipelineService.profileSummary(profile)` = `{industry, region_sido, region_sigungu}` **3개뿐**(이슈 #83).
- 매출·업력·직원수·자금용도·희망금액은 L5에 직접 전달되지 않고, **오직 fit_text(L3 의역)를 통해서만** 들어감 → 1-1의 오류가 그대로 전파되는 통로.
- 또한 `report_gen.py`의 user payload는 `matches`에서 **title만** 뽑아 `match_titles`로 넘김. **`match_score`(적합도 %)·`caveats`(유의사항)를 L5에 안 줌** → 본문에서 우선순위를 매기거나 자격 리스크를 반영해 조언할 근거가 없음.

### 1-4. 서술만 하고 조언을 안 함 (어조)

- 현재 보고서는 "~할 수 있습니다 / ~도움이 될 수 있습니다"류의 서술·유보 위주. 무엇을 **먼저** 해야 하는지, 어느 게 자격이 안 맞을 위험이 큰지에 대한 **결정적 조언이 없다.**
- 정작 `정책자금.png` 카드에는 적합도(78% vs 62%)와 유의사항(프렙아카데미는 만 19~39세 미창업자 대상 → 1~3년 운영 중인 사장님과 안 맞을 위험)이 있는데, **본문은 이 신호를 종합하지 않는다.**

## 2. 핵심 통찰 — "반복"이 아니라 "종합(synthesis)"

전문가 느낌의 본질은 데이터를 더 넣는 게 아니라 **이미 나눈 대화 위에서 한 걸음 더 나아가는 것**이다.

- 콜2 시점에 사장님은 **이미 진단을 읽었고, 이미 재질문에 답했다.**
- 그런데 보고서 "지금 상황"이 진단을 **다시 서술**하면, 전문가가 아니라 **녹음기**처럼 읽힌다.
- 보고서는 진단을 반복하지 말고, 답변을 눈에 보이게 접어 넣어 결론을 좁혀야 한다:
  > "말씀하신 **[운영자금 — 재료비·인건비 부담]**을 반영하면, 진단은 이렇게 좁혀집니다 … 그래서 **A를 먼저** 권합니다."
- 따라서 "진단·답변을 데이터로 흘려보낸다"에서 그치면 안 되고, **"답변 1개 이상을 명시적으로 참조하고, 진단을 반복하지 말고 그 위에서 정제하라"를 프롬프트의 명시적 요구사항**으로 박아야 한다.

## 3. 튜닝 전략 — 3단계 (ROI·리스크 순)

각 단계는 독립 배포 가능하도록 쪼갠다. **P1이 신뢰도 파괴 오류를 단독으로 없애고 먼저 검증**된 뒤 더 큰 프롬프트 수술로 넘어간다.

| 단계 | 내용 | ROI | 리스크 |
|---|---|---|---|
| **P1** | 결정론적 프로필 팩트시트 (매출 월/연 오류 박멸) | 최상 (신뢰도 즉시 회복) | 낮음 (필드 추가·결정론적) |
| **P2** | 진단·답변 carry-through + 종합 서사 (전문성 핵심) | 높음 | 중간 (`run` 시그니처·프롬프트 2개) |
| **P3** | 적합도·유의사항 기반 우선순위 조언 + 결정적 어조 | 중간 (마감 폴리시) | 중간 (#76 경계 주의) |

---

### P1 — 결정론적 프로필 팩트시트

**아이디어**: 모델에게 `monthly_revenue_band`처럼 오해를 부르는 원시 필드를 주지 말고, **Spring이 사람이 읽는 라벨로 확정 문장을 조립**해 넘긴다. 기존 `_deadline_note`(D-day를 결정론적으로 미리 계산해 프롬프트에 박는 패턴)와 동일한 접근.

**중요(검토 반영)**: 팩트시트를 **콜1(진단)과 콜2(보고서) 양쪽에 동일하게** 적용한다. 지금 두 콜은 매출 포맷을 공유하는 로직이 없어 각자 월/연을 독립적으로 (오)해석한다 → 한쪽만 고치면 **두 화면에서 서로 다른 매출 표기가 나오는 정합성 버그**가 생긴다.

**결정하지 않음(대안)**: 컬럼명 `monthly_revenue_band`를 리네임 → 이 컬럼을 읽는 모든 코드/마이그레이션을 건드려야 해 리스크 큼. 팩트시트로 우회.

**구현 지점**
- 신규: api-core에 공유 순수 함수 `ProfileFacts.compose(Map profile) -> String` (JdbcTemplate 불필요, `PipelineServiceTest`가 쓰는 정적 헬퍼 패턴과 동일하게 테스트 가능).
  - 매출: `revenue_basis == "ANNUAL"` → `"연매출: 1억~3억"`, `"MONTHLY"` → `"월평균 매출: 1억~3억"`, null/미상 → 라벨 없이 밴드만
  - `업력: 1~3년`, `직원 수: 1~4명`, `자금 용도: 운영자금`(funding_purpose 리스트 → 라벨), `희망 자금: 1천만~5천만`
  - 체납/연체/수혜이력: 값이 있을 때만 포함 (없음도 넣을지는 §5 결정사항)
- 배선:
  - 콜1: `ConsultationService.diagnose` → `/diagnose` payload에 `profile_facts` 추가
  - 콜2: `PipelineService.run` → `/analysis`(L3)와 `/report/generate`(L5) payload에 `profile_facts` 추가
- ai-engine 프롬프트(`diagnosis.py`·`cause_analysis.py`·`report_gen.py`) 공통 지시 추가:
  > "profile_facts는 확정된 라벨 사실이다. 매출은 반드시 이 라벨(연매출/월평균)을 그대로 쓰고, 원시 필드명으로 월/연을 추정하지 마라."

**테스트**
- `ProfileFacts` 단위 테스트: ANNUAL/MONTHLY/null, funding_purpose 리스트, 리스크 필드 유무
- ai-engine: 각 서비스 payload에 `profile_facts` 포함 / 프롬프트에 "라벨 신뢰" 지시 포함 (기존 `test_system_prompt_*` 방식)

### P2 — 진단·답변 carry-through + 종합 서사

**아이디어**: 콜2가 만든 진단과 사장님 답변을 매칭에서 끝내지 말고 **L3·L5까지 흘려** 설명·보고서에 반영한다.

**배선 결정(검토 반영 — 무엇을 어디로)**
- **답변 → L3(`explain_fit`)**: 사장님이 답한 내용으로 공고별 `match_rationales`(reason)를 더 뾰족하게. 예: 자금용도가 "시설"이면 시설자금 성격 공고의 reason을 그쪽으로 강조.
- **진단 + 답변 → L5(`report_gen`)**: 서사·조언 담당. "지금 상황"을 진단 반복이 아니라 그 위에서 정제하고, **답변 1개 이상을 명시적으로 반영**.
- **배치/데일리 리포트는 얇게 유지**: 그 경로엔 진단·답변이 없다. `run`에 nullable 선택 인자로 넣어, null이면 현재 동작(얇은 리포트)으로 폴백 → 나중에 "왜 배치 리포트는 다르냐"가 회귀로 오인되지 않게 문서화.

**구현 지점**
- `PipelineService.run(long profileId, List matches)` → `run(long profileId, List matches, String diagnosisText, List followUpAnswers)` (배치 호출부는 `null, null`)
- `ConsultationService.specialize`: `session.diagnosis_text` + 답변을 `run(...)`에 전달
- `AiEngineClient.analyze` / `generateReport`: `diagnosis`·`answers` 선택 필드 추가 (null이면 미전송 — 기존 컨벤션과 동일)
- 프롬프트:
  - `cause_analysis.py`: "answers가 있으면 각 공고 reason을 사장님이 말한 필요에 맞춰 구체화하라"
  - `report_gen.py`: "지금 상황은 진단을 반복하지 말고 그 위에서 한 걸음 나아가라. 사장님이 답한 내용 최소 1개를 명시적으로 반영해 '답변 → 결론' 연결을 보여줘라. 진단에 이미 나온 상권·경기 해석은 근거로 활용하되 통째로 복붙하지 마라."

**테스트**
- `run` null 경로 vs 값 전달 경로
- `report_gen`/`cause_analysis` payload에 diagnosis/answers 포함(있을 때)·미포함(null일 때)
- 프롬프트에 종합·답변참조 지시 포함
- 주관 축(답변 참조·반복 아닌 정제)은 §4의 골든 before/after LLM 심사로

---

### P3 — 우선순위 조언 + 결정적 어조

**아이디어**: 카드에 이미 있는 적합도·유의사항을 **본문이 종합**해, 무엇을 먼저 할지 분명히 조언한다.

**구현 지점**
- `report_gen.py` user payload에 공고별 **압축 힌트**만 추가: `{title, match_score, has_caveats}` (유의사항 원문 전체가 아니라 "있음/없음" 플래그 + 적합도). 원문 유의사항·마감일·링크는 카드 전담(#76) — 본문 중복 금지.
- 프롬프트:
  > "적합도(match_score)가 높은 공고를 먼저 권하라. has_caveats가 있는(자격 불확실) 공고는 '먼저 요건 확인'으로 톤을 낮춰라. 서술이 아니라 조언으로: '무엇을 먼저 하세요'를 분명히. 단, 각 공고의 지원대상·마감일·링크·유의사항 원문은 카드가 전담하므로 본문에서 반복하지 마라(#76)."
- 마지막에 짧은 **"다음 한 걸음"** 조언(우선순위 + 확인할 요건 1~2개).

**테스트**
- payload에 `match_score`·`has_caveats` 포함
- **#76 가드 유지**: 기존 `test_generate_report_sends_only_count_not_per_match_details`가 검증하는 "deadline_note/detail_url 미전송"은 그대로 통과해야 함
- 본문이 마감일·링크·유의사항 원문을 복붙하지 않는지는 골든 LLM 심사로

## 4. 검증 방법 (주관적 목표를 판정 가능하게)

"전문가 느낌"은 단위 테스트가 안 되므로 **결정론 + 골든 심사**로 쪼갠다.

### 4-1. 결정론적 단위 테스트 (자동)
- `ProfileFacts`: ANNUAL→"연매출", MONTHLY→"월평균", funding_purpose 라벨 매핑
- payload 조립: 있을 때 `profile_facts`/`diagnosis`/`answers`/`match_score` 포함, null일 때 미포함
- **경계 가드(#76)**: `deadline_note`/`detail_url` 미전송 테스트 유지
- 프롬프트-포함 어서션: 라벨 신뢰 지시, 종합·답변참조 지시, 우선순위 지시

### 4-2. 골든 프로필 before/after (수동 or LLM 심사)
- **고정 프로필**: 강남구 카페 (business_profile id=6, `doc/screenshots/온보딩.png`)
- **"before" 기준물**: 현재 `doc/screenshots/보고서.png` + 아래 문제 문장 (이 문서에 박제)
  - ❌ "월 1억~3억" (연매출인데 월로 오표기)
  - ❌ 상권·경기·재질문 답변 반영 0
  - ❌ 우선순위·다음 액션 없음
- **"after"**: P2/P3 적용 후 동일 프로필로 재생성
- **심사 축**: ① 정밀성(매출 정확?) ② 개인화(답변·진단 반영?) ③ 조언성(우선순위·액션?) ④ 경계 준수(#76 카드 중복 없음?) ⑤ 어조(결정적이되 정직?)
- 심사 주체: `/ask codex` 또는 LLM 저지, 최종 눈 확인

## 5. 결정 필요 사항 (구현 착수 전 확인)

1. **팩트시트에 "체납 없음/연체 없음"을 긍정 신호로 넣을지** vs 생략(잡음 최소화). — 현재 보고서는 "깨끗한 신용"을 강조하니 넣는 쪽이 어울려 보임.
2. **본문에서 마감 임박을 정성적으로 언급 허용할지**("마감이 가까운 것부터") vs 마감일은 카드 전담 유지(#76 엄격). — 안전하게 카드 전담 권장, 필요 시 urgent 불리언만 전달.
3. **배치/데일리 리포트도 같은 어조로 끌어올릴지** vs 얇게 유지(진단이 없어 종합 불가). — 얇게 유지 권장.
4. **P1이 콜1 진단 프롬프트도 건드리므로**, 진단 품질(재질문 생성 안정성 포함)이 회귀하지 않는지 P1 배포 후 별도 확인 필요.

---

## 6. 범위 밖 (이번 튜닝에서 건드리지 않음)

- 결과 **양식**(진단 카드·정책자금 카드·적합도 바·초안 생성 버튼)은 사장님이 만족 → 그대로 둔다.
- 매칭 로직(`hybrid_search`·하드필터·RRF)·`match_relevance` 산정 규칙 — 건드리지 않음.
- 신청서 초안(`draft`) 기능 — 별개.
