## 1. 서비스 전체 그림 (배경 지식 없이 읽는 개요)

### 1-1. 한 문단 요약

**소상공인 금융 지원 에이전트**는 사장님이 온보딩 질문지(업종·지역·매출·자금 상황 등)에 한 번 답하면, AI가 그 프로필을 바탕으로 **먼저** 경영 진단을 해주고, 사장님에게 맞는 정책자금 공고를 자동으로 찾아 근거와 함께 추천하고, 신청서 초안까지 써주는 서비스입니다. 사용자가 매번 검색하지 않아도 새로운 정책자금이 나오면 시스템이 알아서 매칭해 알려준다는 게 핵심입니다("능동형" 서비스 — 아래 §2-1에서 자세히).

### 1-2. 실제 사용 흐름 (사용자 입장)

1. 회원가입 → 온보딩 질문지 작성(업종, 지역, 매출, 세금 체납 여부, 자금 필요 이유 등 9개 문항)
2. 제출하면 AI(Claude Opus)가 그 자리에서 "지금 이 사장님 상황이 어떤지" 진단문을 써주고, 애매한 부분은 2~4개의 확인 질문을 되묻습니다.
3. 사장님이 질문에 답하면(또는 건너뛰면), AI(Claude Sonnet)가 그 답변까지 반영해 어울리는 정책자금을 찾고, 왜 이 공고가 맞는지 근거를 붙인 리포트를 만들어줍니다.
4. 리포트 화면에서 마음에 드는 공고를 고르면, 신청서 초안(사업개요·신청사유·활용계획·기대효과)을 AI가 미리 써줍니다. 실제 제출은 사장님이 검토 후 직접 합니다(자동 제출 기능은 의도적으로 만들지 않음).
5. 이후에도 배치가 매시간 돌면서 새 정책자금이 나오면 알림(앱 내 알림 + 카카오톡)으로 먼저 알려줍니다.

### 1-3. 시스템 구성 (3개 서비스)

| 구성요소 | 역할 | 비유 |
| --- | --- | --- |
| 웹 프론트엔드(Next.js) | 사장님이 보는 화면 | 매장의 "카운터" |
| 백엔드(Spring Boot) | 회원 정보·프로필·리포트를 저장하고, 전체 흐름을 지휘 | 매장의 "주방 총괄" — 유일하게 데이터를 갖고 있고 모든 걸 지시 |
| AI 서비스(FastAPI + Python) | Claude를 호출해서 진단문·매칭·리포트를 만들어내는 역할만 함, 자기가 회원 정보를 직접 들여다보지 않음 | "조리 담당" — 재료(정보)는 주방 총괄이 가져다줘야만 요리(결과)를 만듦 |

이렇게 역할을 명확히 나눈 이유(§2-4에서 더 자세히): AI 서비스가 회원 데이터를 직접 만지지 않게 해서, 나중에 AI 부분만 따로 바꾸거나 확장하기 쉽게 만들기 위함입니다.

## 2. 예선 평가 기준별 참고 자료

## 2-1. 문제 정의 및 필요성 (15점)

**사실**:
- 소상공인은 경영에 영향을 주는 정보(상권 변화, 금리 변동, 새 정책자금 공고)를 놓치기 쉽습니다. 정보가 없는 게 아니라, **여러 곳에 흩어져 있고 변화가 생겼을 때 먼저 알려주는 사람/서비스가 없다**는 게 진짜 문제입니다.
- KB국민은행이 이미 운영 중인 소상공인 서비스를 조사했더니, 전부 "사용자가 먼저 찾아봐야 하는" 구조였습니다.

| 기존 서비스 | 한계 |
| --- | --- |
| 상권분석시스템(KB부동산 Liiv ON) | 조회한 시점의 스냅샷만 줌 — 이후 변화가 생겨도 다시 알려주지 않음 |
| 우리가게 매출순위·신용도(스타기업뱅킹) | 사용자가 직접 앱을 열어야 확인 가능 — 이상 신호를 먼저 알려주는 기능 없음 |
| KB 소호 컨설팅센터 | 전국 13개 센터 예약제 상담 — 상시 모니터링이 구조적으로 불가능 |
| KB상권활성화지수 | 지자체·기업 대상 분석 도구 — 개별 소상공인이 쓰는 서비스가 아님 |
| (참고) 경쟁사 하나은행 | AI 기반 정책자금 맞춤 조회 서비스를 이미 운영 중으로 확인됨 |

**쓰면 좋은 포인트**: "이 서비스는 KB가 이미 갖고 있는 기능(상권분석·매출진단·컨설팅·정책자금 안내)을 대체하는 게 아니라, 흩어진 걸 **상시 감시 + 자동 알림 + 통합 판단**하는 하나의 에이전트로 엮었다"는 게 핵심 차별점입니다. 새 데이터를 만든 게 아니라 기존 기능들 사이의 빈틈(능동적으로 알려주는 주체의 부재)을 메웠다는 논리로 쓰면 좋습니다.

## 2-2. 아이디어의 활용 가능성 (15점)

**사실**:
- 업종·지역을 코드에 못 박아두지 않았습니다. 온보딩에서 업종·지역을 자유 입력받고, 알림 시간도 사용자별로 다르게 설정할 수 있습니다 — 특정 업종·특정 동네 한정 서비스가 아니라 구조적으로 확장 가능합니다.
- 회원가입/로그인, 사용자별 이력 관리까지 이미 구현돼 있어 "1인 데모"가 아니라 여러 사용자를 전제로 한 구조입니다.
- 사용한 외부 데이터가 전부 무료 공공 API(기업마당 정책자금 공고, 한국은행 경기지표)라서, 다른 지역·업종으로 확장할 때 드는 비용을 예측하기 쉽습니다.
- "온보딩 → 능동 매칭 → 근거 있는 추천 → 대화로 다듬기 → 실행 가능한 결과물(신청서 초안)"이라는 구조 자체는 정책자금에만 묶여 있지 않습니다. 소상공인이 놓치기 쉬운 다른 영역(세무, 법률, 노무 관련 지원제도 등)에도 같은 틀을 재사용할 수 있습니다.

**쓰면 좋은 포인트**: KB의 기존 대출 상담·컨설팅센터로 자연스럽게 이어질 수 있는 연계 지점이라는 것, 그리고 특정 업종·지역에 한정된 프로토타입이 아니라 구조적으로 확장 가능하다는 걸 강조하면 좋습니다.

## 2-3. 아이디어의 창의성 및 효과 (20점)

**사실 (에피소드 형태로 정리했습니다 — 이런 사례가 "창의성/효과"를 설명하기 좋습니다)**:

1. **반응형이 아니라 능동형**: 위 2-1에서 봤듯 기존 서비스는 다 사용자가 먼저 확인해야 하는데, 이 서비스는 배치가 매시간 돌면서 신규 정책자금을 먼저 찾아 알려줍니다.
2. **1번에 끝내지 않고 대화로 다듬는 구조**: 온보딩 직후 바로 리포트를 주지 않고, 먼저 AI가 진단문을 주고 사장님에게 2~4개를 되묻습니다. 그 답변이 실제로 추천 결과에 반영됩니다. "내가 방금 답한 게 결과에 반영된다"는 체감을 만드는 설계로, "자동 생성 리포트가 사장님 상황을 충분히 못 담는다"는 문제를 풀려고 도입했습니다.
3. **AI를 못 믿는다는 전제로 설계**: 개발 중 실제로 "AI가 신청 자격이 안 되는 공고에도 점수를 매겨버리는" 사례를 발견했습니다. 프롬프트로 "이러지 마라"고 지시하는 것만으론 안 통해서, AI 응답을 받는 두 지점(AI 서비스 쪽, 백엔드 쪽) 모두에서 각각 독립적으로 다시 검증해서 강제로 걸러내는 이중 장치를 만들었습니다. "AI가 알아서 잘하겠지"가 아니라 "AI가 틀릴 수 있다는 전제로 시스템을 짠다"는 설계 철학을 보여주는 사례입니다.
4. **스스로 발견하고 고친 UX 문제**: 실제 사용 데이터를 검토하다가, 배치가 재매칭할 때마다 리포트가 "이번에 새로 찾은 것만" 보여주는 방식이 두 가지 문제를 만드는 걸 발견했습니다 — ① 오래전에 나온 공고인데 순위만 조금 바뀌어도 "새로 찾음"으로 잘못 표시되는 문제, ② 리포트마다 추천 목록이 통째로 바뀌어서 사장님이 "이전 추천이랑 다른 결과가 나왔다"고 오해할 수 있는 문제. 이걸 "지금까지 추천된 것 전체를 다시 줄 세운 누적 목록"으로 재설계하고, "새 공고" 표시 기준도 재검토해서 "실제로 알려드린 지 3일 이내"라는 시간 기준으로 다시 다듬었습니다. **외부 사용자 피드백이 아니라 스스로 실사용 데이터를 검토해서 제품 결함을 찾고 고친 사례**라 강조할 만합니다.
5. **정보 제공에서 한 발 더 나아감**: 대부분의 정책자금 서비스는 "이런 지원사업이 있다"까지만 알려줍니다. 이 서비스는 신청서 초안까지 AI가 써줘서 실제 신청 행동으로 이어지게 합니다. 단, 실제 제출은 사장님 몫으로 명확히 남겨서(자동 제출 없음) 책임 소재를 분리했습니다.
6. **장애에 강한 알림**: 앱 내 알림(필수 경로)과 카카오톡 알림(선택 경로)을 나눠서, 카카오 쪽에 문제가 생겨도 핵심 알림 기능은 안 죽게 만들었습니다.

**쓰면 좋은 포인트**: 특히 4번(스스로 문제를 찾고 고친 사례)은 "AI를 개발에 활용해 반복 개선한 과정" 자체를 보여주는 좋은 소재라, 창의성/효과 항목뿐 아니라 다른 항목(개발 계획의 구체성 등)에도 겹쳐서 쓸 수 있습니다.

## 2-4. 기술 적정성 (20점)

**사실**:
- 3개 서비스(프론트엔드/백엔드/AI서비스)로 역할을 나누고, "AI 호출은 반드시 백엔드를 거쳐 AI 서비스로" 라는 규칙을 코드로 강제했습니다. 백엔드 코드에는 Claude 관련 라이브러리가 아예 설치돼 있지 않습니다 — 구조적으로 다른 경로로 AI를 부를 수 없게 만든 것입니다.
- AI 모델을 하나만 쓰지 않고 3단계(Opus/Sonnet/Haiku)로 나눠 썼습니다. 기준은 "비용"이 아니라 **"이 단계가 틀리면 이후 전체가 틀어지는가"**입니다.

| 모델 | 쓰인 곳 | 이유 |
| --- | --- | --- |
| Claude Opus (가장 고성능) | 첫 진단문 작성 (1곳) | 이후 재질문·매칭·리포트 전체의 출발점이라 품질이 제일 중요 |
| Claude Sonnet (중간) | 공고 적합성 판단, 리포트 작성, 신청서 초안 (3곳) | 판단·글쓰기가 필요한 작업 |
| Claude Haiku (가벼움) | 검색어 다듬기 (1곳) | 판단이 아니라 단순 변환 작업이라 가벼운 모델로 충분 |

- 정책자금 검색은 AI에게만 맡기지 않았습니다. 키워드 검색(한국어 형태소 분석 기반)과 의미 기반 벡터 검색을 함께 돌려서 결과를 합치고, AI는 그렇게 추려진 후보를 "판단하고 설명하는" 역할만 합니다. 지역·업종이 맞는지, 마감일이 지났는지처럼 명확하게 판정 가능한 건 전부 코드가 계산합니다 — AI에게 정확성이 중요한 계산을 맡기지 않았습니다.
- 벡터 검색 저장소는 여러 후보(Chroma, pgvector 등) 중 Chroma를 선택했는데, 그 이유를 문서로 남겨뒀습니다 — 한국어 임베딩 모델을 직접 지정할 수 있어 한국어 검색 품질을 높이기 쉬웠고, MVP 기간(4주) 내에 다른 걸로 바꾸면 AI 서비스를 통째로 다시 짜야 해서 위험 대비 이득이 낮다고 판단했습니다.
- AI가 규칙을 어길 수 있다는 전제로, 부적격 공고에 점수가 붙는 걸 코드가 두 곳(AI 서비스·백엔드)에서 각각 다시 검증해서 강제로 지웁니다. 이 검증 로직은 자동화된 테스트로도 고정돼 있어서, 나중에 누가 실수로 이 로직을 지워도 테스트가 실패하면서 바로 드러납니다.
- 운영에 필요한 것들도 갖췄습니다: 반복되는 프롬프트는 캐싱해서 비용을 아끼고, 모든 AI 호출마다 토큰 사용량을 로그로 남기고, 응답이 중간에 잘렸는지 감지하고, "AI를 실제로 부르지 않고 가짜 응답으로 전체 배선만 확인하는" 테스트 스위치도 만들어뒀습니다.

**쓰면 좋은 포인트**: "AI를 무조건 많이 쓴 게 아니라, AI가 필요한 곳과 코드로 확실하게 처리할 수 있는 곳을 구분해서 썼다"는 게 기술 적정성의 핵심 논리로 쓰기 좋습니다.

## 2-5. 개발 계획의 구체성 (15점)

**사실**:
- 처음 기획 단계부터 "1개 업종 × 1개 지역 시나리오에서 전체 흐름이 실제 데이터로 끝까지 동작하는 것"을 목표로 잡고, 확보하기 어려운 데이터(카드사 소비 데이터 등)는 처음부터 대체 지표로 처리하기로 미리 정해뒀습니다. 넓게 벌리다 일부가 가짜 데이터로 채워지는 것보다, 좁더라도 확실하게 도는 걸 우선순위로 삼았습니다.
- 기능 하나하나를 이슈(작업 항목)로 먼저 정의하고, 이슈별로 별도 작업 공간에서 구현한 뒤 병합하는 방식을 처음부터 끝까지 유지했습니다. 그래서 "왜 이렇게 바꿨는지"가 전부 기록으로 남아있습니다. 예: "임계값 기반 알림을 프로필 기반 매칭으로 전환"은 특정 이슈 번호로, "부적격 공고 사전 배제"는 다른 이슈 번호로 각각 추적됩니다.
- 계획이 고정된 문서가 아니라 실측 결과를 근거로 계속 조정됐습니다. 예를 들어 "상권·경기지표 같은 전국 공통 지표는 사용자별로 다르게 알림 주는 기준으로 쓰기 어렵다"는 걸 깨닫고 알림 방식 자체를 전면 재설계한 것, "자동 생성 리포트가 사장님 상황을 충분히 못 담는다"는 걸 깨닫고 대화형으로 바꾼 것 등, 최소 3차례의 큰 방향 전환이 각각 이유와 함께 문서로 남아있습니다.
- 개발 자체를 역할별로 나눠서(백엔드 담당/AI 담당/프론트엔드 담당/검증 담당) 서로 의존하지 않는 작업은 동시에 진행하는 방식을 썼습니다. 이게 실제로 동시에 진행됐다는 건 작업 항목들이 생성되고 종료된 시각이 겹치는 것으로 확인할 수 있습니다(예: 3개 작업이 20여 초 간격으로 연달아 열리고 16초 안에 함께 닫힌 사례).

**쓰면 좋은 포인트**: "계획을 세우고 그대로 밀어붙인 게 아니라, 실측 데이터를 근거로 계획 자체를 갱신하며 개발했다"는 걸 보여주는 게 다른 팀과 차별화되는 포인트입니다. 무작정 일정만 지킨 게 아니라 판단 근거가 있었다는 걸 강조하세요.

## 2-6. 기술 실현 가능성 (15점)

**사실**:
- 개념 증명(PoC) 수준이 아니라, 온보딩부터 진단·매칭·리포트 생성·저장·알림까지 전체 흐름이 실제로 동작하는 코드로 완성돼 있습니다. 배치(매일 새벽 데이터 수집, 매시간 재매칭)도 실제로 스케줄러에 등록돼 돌아갑니다.
- 실제 정부 공공 데이터로 검증했습니다 — 기업마당(정책자금 공고)에서 실데이터 1,500여 건을 가져와 검색 가능한 형태로 색인해뒀고, 실제 회원 계정으로 매칭·리포트 생성까지 확인했습니다. 목업 데이터가 아닙니다.
- 개발 중 실제로 부딪힌 문제와 그 해결 과정을 기록으로 남겼습니다 (아래는 전부 실제로 발생 → 원인 파악 → 해결까지 완료된 사례입니다):
  - AI가 규칙을 어기는 사례를 발견해서 코드로 이중 검증하도록 고침
  - 특정 AI 모델에서 응답 형식을 강제하는 기법이 아예 거부당하는 걸 실측으로 확인하고 다른 방식으로 교체
  - 처리 시간이 대기 제한 시간과 거의 맞붙어서 "아직 처리 중인데 완료된 것처럼" 보이는 문제를 발견 → 1차로 대기 시간을 늘리는 임시 조치 → 이후 아예 구조를 바꿔서(폴링 대신 결과를 직접 기다리는 방식) 문제 유형 자체를 없앰
  - 실제 리포트 데이터를 비교하다가 "새 공고" 판정 로직의 결함을 스스로 찾아내 개선
- **기술부채도 숨기지 않고 정리했습니다**: 상권 데이터를 수집하는 기능 하나가 온보딩에서 실제로 쓰는 값과 체계가 달라 사실상 한 번도 정상 동작한 적이 없다는 걸 스스로 조사해서 발견했습니다. 어설프게 고치는 대신, 제대로 고치려면 필요한 인프라(주소를 좌표로 변환하는 작업 등)가 갖춰져 있지 않고 핵심 기능과도 무관하다고 판단해 **기능 자체를 코드에서 완전히 삭제**했습니다. "일단 만들어놓고 안 되는 채로 두는" 대신, 안 되는 걸 확인하면 정직하게 걷어내는 방식으로 코드를 관리했다는 근거입니다.
- 자동화된 테스트(AI 서비스 쪽 90여 건, 백엔드 쪽 단위 테스트)를 변경할 때마다 돌려서 확인하는 걸 습관으로 유지했습니다. "구현했다"가 아니라 "테스트로 확인했다"는 근거를 남기는 방식입니다.

**쓰면 좋은 포인트**: "이미 돌아가는 시스템에서 실제로 발견한 문제를 실제로 고친 이력"이 있다는 것 자체가 "이 프로젝트가 실현 가능하다"는 가장 강력한 증거입니다 — 아직 안 만들어본 계획이 아니라, 이미 만들고 써보고 고친 결과물이라는 걸 강조하세요.

## 4. 자주 나오는 용어 설명

| 용어 | 뜻 |
| --- | --- |
| 온보딩 | 처음 가입할 때 사업 정보(업종·지역·매출 등)를 입력받는 질문지 과정 |
| 능동형(proactive) | 사용자가 찾지 않아도 시스템이 먼저 감지해서 알려주는 방식. 반대말은 "반응형"(사용자가 검색해야 답이 나오는 방식) |
| 매칭 | 정책자금 공고 중에서 이 사장님 프로필에 맞는 걸 찾아내는 과정 |
| 하이브리드 검색 | 키워드로 찾는 방식과 의미(뜻)로 찾는 방식을 둘 다 써서 결과를 합치는 검색 방법 |
| RAG | 검색으로 관련 정보를 먼저 찾은 뒤, 그 정보를 AI에게 주고 답을 만들게 하는 방식. AI가 아무것도 없이 혼자 지어내지 않게 하는 기법 |
| Opus / Sonnet / Haiku | Claude(Anthropic의 AI 모델)의 등급 이름. Opus가 가장 고성능(느리고 비쌈), Haiku가 가장 가벼움(빠르고 저렴), Sonnet은 중간 |
| 이중 검증 | AI가 낸 답이 틀렸을 가능성을 감안해서, 코드가 그 답을 한 번 더 확인하고 필요하면 강제로 고치는 방식 |
| 배치(batch) | 사람이 직접 누르지 않아도 정해진 시간마다 자동으로 실행되는 작업(예: 매일 새벽 정책자금 새로 수집하기) |
